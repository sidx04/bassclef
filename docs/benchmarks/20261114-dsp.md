# SplitFrames: copy to alias

| | |
| --- | --- |
| Date | 14th November, 2026 |
| Files | `internal/dsp/frames.go` |
| Benchmark | `BenchmarkSplitFrames` (`internal/dsp/bench_test.go`) |

## Summary

| | Before (copy) | After (alias) |
| --- | --- | --- |
| Time/op (mean of 10) | 12.04 ms | 8.88 µs |
| Memory/op | 169.4 MB | 128 KiB |
| Allocs/op | 5,167 | 1 |

Removing the per-frame copy makes `SplitFrames` about 1,350x faster and cuts its memory by about 1,290x. The main gain is memory, not time; see [End-to-end impact](#end-to-end-impact).

## Change

The old `extractSplitFrames()` allocated a new slice for every frame and copied the samples into it. With the default hop (half the frame size), every sample lands in two frames, so the copied frames took 169 MB for an 85 MB input: about 2x the input size, allocated on top of `samples`.

```go
func extractSplitFrames(samples []float64, frameSize int, hopSize int) [][]float64 {
	...
	for start := 0; start+frameSize <= len(samples); start += hopSize {
		frame := make([]float64, frameSize)
		copy(frame, samples[start:start+frameSize])
		frames = append(frames, frame)
	}
	...
}
```

The copy protected nothing. No caller of `SplitFrames` mutates the frames; `Spectrogram` copies each frame into its own `windowed` slice before `applyWindow` multiplies the window in place (`internal/dsp/spectrogram.go`).

The new version aliases into `samples` instead of copying:

```go
func extractSplitFrames(samples []float64, frameSize int, hopSize int) [][]float64 {
	...
	for idx := 0; idx+frameSize <= len(samples); idx += hopSize {
		frames = append(frames, samples[idx:idx+frameSize:idx+frameSize])
	}
	...
}
```

The 3-index slice caps each frame's capacity at `frameSize`, so an `append` on one frame allocates a new array instead of overwriting the next frame.

### Why one allocation remains

The one remaining allocation is the outer `[][]float64` that holds the frame headers. Each slice header is 24 bytes (pointer, length, capacity), so 5,166 frames need 123,984 bytes, which the Go allocator rounds up to 131,072 bytes (16 pages of 8 KiB). The per-frame allocations are gone.

## Tradeoffs

- **Frames share memory with `samples`.** Any in-place change to `samples` after the split shows up in the frames. This does not affect the current code: `fingerprint.FromBuffer` calls `NormalizeGain` *before* `SplitFrames` (`internal/fingerprint/pipeline.go`). Keep that order: moving `NormalizeGain` after the split would  change the frames.
- **Frames keep the whole `samples` array alive.** A frame is a view into the backing array of `samples`, so the garbage collector cannot free that array while any frame is reachable. Holding one 32 KiB frame pins the full 85 MB array. This does not cost extra today: every caller (`FromBuffer` and the `spectrogram` / `peaks` / `fingerprint` CLI commands) uses the frames only inside the function, while `buf` is still in scope, and drops them on return.

## Setup

- Input: synthetic 240 seconds signal at 44,100 Hz (`createBenchSignals`): 10,584,000 samples, 85 MB as `float64`
- Config: `DefaultConfig()` -> FFT size 4096, hop 2048, which gives 5,166 frames
- Go 1.27.1, darwin/arm64, Apple M5
- 10 runs per version (`-count=10`)

The "before" numbers come from the copy version of `frames.go` at commit [8dcbb710](https://github.com/sidx04/bassclef/commit/8dcbb710efd37dd105d083db886d8f58a9bd3375).
Reproduce:

```sh
go test -run '^$' -bench '^BenchmarkSplitFrames$' -count=10 ./internal/dsp/ > new.txt
```

To compare with a proper statistical test, save a "before" run the same way and use [`benchstat`](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat) (not used for this report):

```sh
go install golang.org/x/perf/cmd/benchstat@latest
benchstat old.txt new.txt
```

## End-to-end impact

The 1,350x speedup applies to `SplitFrames` only. On the same input, `BenchmarkSpectrogram` takes about 612 ms/op (single run), so the 12 ms saved is about 2% of the DSP stage.

The bigger win is memory. Every ingest and every query used to allocate a 169 MB short-lived heap spike just to hold frames, which the garbage collector then had to clean up. That spike is now gone.

## Next target

`Spectrogram` is now the main allocator in `internal/dsp`. On the same input it allocates about 1,016 MB/op across 20,666 allocs/op (single run). For every frame it allocates:

- the `windowed` copy of the frame
- the FFT output (`[]complex128`)
- the `Magnitude` result

Reusing one `windowed` buffer across frames, and checking whether the FFT can write into a caller-provided buffer, would cut most of this.
